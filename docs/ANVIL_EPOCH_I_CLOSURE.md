# PROJECT ANVIL — Epoch I Closure

Status: **CLOSURE IN PROGRESS — BASELINE FROZEN**

This is a one-time transition record for closing the ANVIL-00…10 research epoch before the first owner-facing Physical Fabric Workbench. It is not a live roadmap and does not supersede `.anvil/project-state.json` or `docs/CURRENT_HANDOFF.md`.

## Why this closure exists

ANVIL-00…10 established a bounded capability chain from persistent authored matter through disposable rigid topology, local passive/active semantics, compliant response, transient activation and semantic re-lowering after one topology change.

The next useful question is no longer automatically another isolated ANVIL-NN falsifier. Before adding new physics or ontology, the project will expose already accepted capabilities in a small owner-facing **Physical Fabric Workbench v0** so the owner can directly judge whether the accumulated stack begins to express the intended Machine Matter / Physical Fabric idea.

The Workbench is an integration/owner-value stage, not ANVIL-11 and not a new scientific capability claim by itself.

## Closure invariant

**No cleanup or integration-preparation change may silently alter the scientific semantics of ANVIL-00…10.**

If a proposed cleanup requires changing accepted experiment/compiler/runtime behavior, physical thresholds, authored meaning or foundation semantics, stop closure work and reclassify the change before proceeding.

Historical preflights, evidence logs, amendments and meaningful negative evidence are preserved.

## Work classes after Epoch I

ANVIL distinguishes these material work types:

1. **experiment** — asks a new falsifiable scientific/semantic/physics question and may earn a bounded capability;
2. **foundation** — promotes or hardens a reusable boundary already supported by evidence, without inventing a new physical answer;
3. **integration** — composes already accepted capabilities for owner-facing or system-level evaluation; green integration does not automatically create a new scientific claim;
4. **maintenance** — changes tooling, process, packaging, documentation or neutral infrastructure while preserving accepted semantics.

If integration or maintenance reveals a new scientific uncertainty, stop and create a separate experiment rather than smuggling the answer into integration code.

## Closure checkpoints

### C0 — baseline freeze

- resolve live `main` and accepted provenance;
- confirm no active experiment/PR;
- record branch inventory and known process debt;
- freeze the no-semantic-change boundary.

### C1 — truth and governance reset

### C2 — infrastructure hygiene

- remove the false assumption that every production artifact represents one historical active ANVIL scientific gate;
- preserve exact artifact provenance and safe owner launching;
- remove manual test-registration omission risk;
- clean stale operational prose where it can mislead takeover;
- do not refactor accepted experiment semantics for DRYness.

### C3 — repository hygiene

Classify every non-main branch before deletion:

- A — fully reachable from `main`;
- B — unique commits but content/provenance is safely preserved canonically elsewhere;
- C — unique scientific/process evidence worth retaining;
- D — still technically required;
- E — unclear; retain until understood.

Delete only branches whose loss is demonstrably harmless.

## Final closure gate

Epoch I is closed only when all are true:

- accepted scientific truth remains exactly through ANVIL-10 with no broadened claim;
- no canonical document instructs a new agent to start TORQUE-PATCH-REPRESENTATION by inheritance;
- state, handoff, memory and README agree on the Epoch I → Workbench transition;
- infrastructure regressions are green after cleanup;
- historical evidence remains reproducible and discoverable;
- branch history is classified before any deletion;
- a new conversation can cold-takeover the repository and correctly conclude that the next stage is **Physical Fabric Workbench v0**, not ANVIL-11;
- Workbench is explicitly forbidden from inventing generic Machine Matter ontology merely to make integration convenient.
